### 👑 [S] obra/superpowers
- **项目地址**: [https://github.com/obra/superpowers](https://github.com/obra/superpowers)
- **基本数据**: `Shell` | ⭐️ 291,272 (611 stars today) | **来源**: `trending`
- **入选理由**: *29 万星的 Agent 技能框架，把软件开发方法论编码为 Agent 可执行的能力单元，是 agentic coding 方法论层面的范式贡献。*

### 核心痛点解决

大多数使用AI编码助手的开发者在任务超出单个提示时会遇到瓶颈。模型会幻想API，忘记三天前文件中的上下文，或者生成技术上可以运行但违反代码库中每个架构原则的代码。根本原因不是模型的能力，而是人类意图与代理执行之间缺乏共享协议。Superpowers通过将软件开发方法论本身固化为离散且可组合的技能，使代理能够可靠地调用这些技能，而不是每次希望模型“自行解决”问题。

### 设计与架构权衡

该框架选择 **shell脚本作为技能运行时**，而不是自定义DSL或Python框架。对于一个“代理型”系统来说，这似乎有些反直觉，但这是一个故意的限制：shell是通用的、可检查的，并且可以通过管道进行组合。每个技能都是一个独立可执行的程序，读取stdin并写入stdout——没有隐藏状态，也没有框架锁定。权衡是失去了结构化数据传递（一切都以文本形式存在），但收益是极大的可移植性：技能可以在CI、本地终端或任何可以启动进程的代理循环中工作。这与Unix哲学相呼应——做好一件事，通过文本流进行组合——应用于代理能力而不是系统工具。

第二个关键决策是 **将方法论作为可执行文档**。技能不仅仅是代码生成器；它们还编码了诸如“先编写失败的测试”或“在实现之前提取接口”之类的流程。代理不仅输出代码，还执行一个技能来强制执行这种纪律。这将负担从“通过提示工程实现正确的行为”转移到“选择合适的技能来适应当前阶段”。牺牲是灵活性：你不能在任务中途轻易偏离规定的方法论。但对于那些在不一致的AI输出中挣扎的团队来说，这种约束是功能。

### 工程见解与可迁移的教训

**基于约束的设计胜过提示工程。**与其希望通过不断加长系统提示来让模型表现良好，不如定义可接受行为的边界作为可执行检查。一个验证“领域层中没有直接数据库调用”的技能可以确定性地捕捉到违规行为——无需模型判断。这种模式可以广泛应用于：每当发现自己在提示工程中应对失败模式时，问问是否可以用代码检查、类型检查或契约测试来强制执行。

**组合性需要统一接口。**Superpowers的所有技能都共享相同的调用签名（stdin/stdout，退出代码）。这使得代理可以在无需自定义粘合代码的情况下将它们链接起来。教训是：在为代理（或人类）构建工具时，首先要标准化 *协议*。十几个具有共享接口的工具比十几个具有自定义API的工具组合效果更好。

**方法论必须是可执行的，而不是理想的。**一张写着“先编写测试”的维基页面在压力下会被忽略。一个在没有失败测试的情况下拒绝继续的技能会改变行为。可迁移的原理是：将团队的不可谈判的规则编码为工作流中的门，而不是文档。

### 生态系统与相关项目

**aider**（25000+星）——一个直接在你的git仓库中操作的AI搭档程序员。Superpowers提供 *方法论*（技能、工作流），而Aider提供 *交互循环*（编辑文件、运行测试、提交）。它们是互补的：Superpowers的技能可以在Aider会话中被调用来强制执行特定的实践。

**langchain**（90000+星）——最初的代理编排框架。Superpowers处于更高的抽象层：LangChain构建代理运行时；Superpowers定义代理在每个步骤应该做什么。可以将Superpowers视为任何代理框架的“软件工程技能标准库”。

**claude-code**（Anthropic的官方CLI代理）——代表了“内置功能”的代理方法，模型处理一切。Superpowers采取了相反的赌注：通过显式技能来约束代理，而不是信任其自发行为。比较这两个项目揭示了代理编程中的基本紧张关系——自主性与护栏——每个团队都需要解决。

### 👑 [S] NousResearch/hermes-agent
- **项目地址**: [https://github.com/NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)
- **基本数据**: `Python` | ⭐️ 248,764 () | **来源**: `llm_giant`
- **入选理由**: *24 万星的自进化 Agent 框架，'与你共同成长'的设计理念在 Agent 记忆与技能积累方向上提供了可落地的工程方案。*

### 核心痛点解决

今天的大多数代理在会话之间是无状态的。你花费数小时教会一个代理你的偏好、你的代码库规范、你的工作流怪癖——然后上下文窗口填满或会话结束，一切都消失了。下一次对话从零开始。核心问题不仅仅是“记忆”在抽象上的问题；而是能够生存于上下文限制并不断演进的结构化、可检索、可组合的知识。构建长期自动化流程的团队经常遇到这个问题：代理在会话中变得越来越聪明，但无法将这些进步延续下去，因此你要么每次都重新教导它，要么构建脆弱的自定义持久层，这些层无法组合。

### 设计与架构权衡

框架将*事件记忆*（发生了什么、何时、什么顺序）与*语义记忆*（提取的事实、学到的技能、用户偏好）以及*程序记忆*（如何做事——可执行技能）区分开来。这不仅仅是分类；它映射到不同的检索策略和不同的TTL策略。事件记忆使用向量搜索和时间衰减——最近的互动更重要，但你仍然可以“回忆”三周前的调试会话。语义记忆以具有显式实体和关系的结构化知识图存储，使精确查询（如“用户的首选错误处理模式是什么？”）成为可能，而不会发生语义漂移。程序记忆存储*可执行*代码片段或工作流，并带有版本控制——当代理学习新技能时，它不仅仅是一个提示模板；而是一个带有测试的可调用函数。权衡在于：这种架构需要比简单地“将一切放入向量数据库”方法更多的前期模式设计和更重的摄入管道。你为了保持读取时间的延迟可预测性和检索精度而付出复杂性成本。

第二个关键决策：*技能提炼发生在冷路径中，而不是在热路径中*。当代理观察到成功的交互模式时，它不会立即尝试泛化——这会阻塞用户并可能导致虚假的抽象。相反，一个后台工作者分析交互踪迹，提出技能候选，运行它们通过验证套件（包括对抗性示例），并在通过后才提升到程序记忆。这意味着用户在会话中通过事件回忆看到即时的能力，而持久的技能则逐渐出现。牺牲在于：“代理曾这样做过”和“代理可靠地作为技能这样做”之间存在延迟。对于高风险自动化，这种延迟是一个功能——它防止了对有缺陷的抽象的过早承诺。

### 工程见解与可转移的教训

**按访问模式，而不是数据类型，分离存储。** 一种诱惑是将“记忆”存储在一个表中，“技能”存储在另一个表中。真正重要的实际上是*如何检索*：时间衰减+相似性搜索用于事件，精确图遍历用于事实，带有版本约束的可执行查找用于技能。每个都需要不同的索引、不同的一致性模型、不同的缓存策略。围绕*查询*设计持久层，而不是对象。

**将学到的技能视为一等可部署的制品，而不是提示片段。** 通过验证的技能获得版本哈希、测试套件、回滚机制和依赖图。当代理“学习”处理API分页的新方法时，该技能可以被审计、在代理之间共享或在API更改时回滚。这将代理学习从“提示工程积累”转变为“以自然语言为源语言的软件工程”。该模式适用于任何从日志中提炼行为的地方：CI/CD管道、数据转换规则、客户支持宏——任何“它曾工作过一次”的地方需要变成“它可靠地工作”。

**明确建模遗忘。** 无界的内存增长会降低检索精度并增加延迟。框架实现*内存压力*信号：当语义图密度超过某个阈值时，会触发合并冗余节点、修剪低置信度边、归档陈旧事件到冷存储。这不是清理；它是核心架构问题。任何从生产流量积累知识的系统都需要内置遗忘策略，而不是事后添加。

### 生态系统与相关项目

**LangGraph**（LangChain）——提供多代理工作流的编排层，带有显式状态管理。hermes-agent关注*长期知识积累*，而LangGraph处理*短期执行控制*——谁调用谁、调用什么状态以及错误如何传播的图。它们可以无缝组合：hermes-agent提供持久记忆后端；LangGraph运行写入它的事件。

**MemGPT**——从操作系统视角解决相同上下文窗口限制：LLM的虚拟内存管理，上下文在固定窗口内进进出出。herme的方法是更高层次的——结构化知识类型与语义检索——而MemGPT是更低层次的——透明上下文分页。当需要与现有单代理循环无缝兼容时使用MemGPT；当构建一个系统时使用hermes-agent，其中*代理知道什么*是一个一等产品关注点。

**AutoGen**（微软）——多代理对话框架，带有代码执行和人机协作。它的强项是*专业代理之间的协作问题解决*。herme的强项是*单个代理在时间上的连续性*。一个常见模式：AutoGen协调一个团队来完成复杂任务；该团队中的每个代理使用hermes-agent的记忆层来保留个人专业知识，跨越调用。

### 👑 [S] deepseek-ai/deepseek-harness
- **项目地址**: [https://github.com/deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)
- **基本数据**: `TypeScript` | ⭐️ 235,296 () | **来源**: `llm_giant`
- **入选理由**: *23 万星的插件化 Agent 架构，'Everything is a Plugin' 的设计哲学让 Agent 能力扩展变得模块化，对构建可组合的 Agent 系统有直接借鉴价值。*

### 核心痛点解决

构建能够真正执行有用工作的代理意味着将语言模型（LLM）、工具、记忆、规划和评估缝合在一起。大多数框架将这些部分硬编码在一起——你得到一个大杂烩，其中更换规划器意味着重写执行器，添加新工具需要修改核心代码。问题不在于编写第一个版本；而是在第六个月，当你需要在三种规划策略和两种记忆后端之间进行A/B测试时，产品团队希望周五能有一个新的工具集成。DeepSeek Harness通过使每种能力——规划、工具使用、记忆，甚至LLM客户端本身——成为具有定义契约的可互换插件来解决这个问题。

### 设计与架构权衡

核心决策是**通过插件注册表实现控制反转**，而不是类层次结构。系统暴露了一个`Plugin`接口，带有生命周期钩子（`initialize`、`execute`、`cleanup`）和能力清单，声明插件提供的和需要的内容。内核在启动时解析依赖关系，通过声明的接口而不是具体类型将插件连接在一起。这种权衡静态类型安全性以换取运行时灵活性——你失去了编译时保证`PlannerPlugin`输出匹配`ExecutorPlugin`输入的保证，但获得了热插拔组件、并行运行多个规划器变体和从外部包加载插件而不必重建核心的能力。注册表也成为交叉切面问题的自然扩展点：日志记录、跟踪、速率限制和成本跟踪都成为包裹其他插件的插件。

第二个权衡出现在**状态管理**中。而不是通过每次调用传递全局上下文对象，每个插件声明自己的状态模式，内核提供隔离命名空间。这防止了“万能上下文”反模式，其中每个组件读写任意键，但它将复杂性推给了插件作者——他们必须显式声明依赖关系并优雅地处理缺失状态。收益是可测试性：具有声明输入/输出的插件可以使用测试数据进行单元测试，集成测试则成为确定性的插件组合。

### 工程见解与可转移的教训

**能力清单胜过隐式契约。**当一个插件声明`provides: ["plan"]`和`requires: ["llm", "memory"]`时，系统可以在启动时验证组合，可视化依赖关系图，甚至自动生成文档。这将架构漂移转化为CI失败。在任何组合服务的地方应用这一点：要求每个模块声明它产生的和消耗的内容，然后让注册表（或构建时检查）验证图的连接。

**生命周期钩子是通用抽象。**`initialize`/`execute`/`cleanup`映射到数据库连接、HTTP客户端、模型预热、缓存填充和关闭。在插件中标准化这一点意味着内核可以正确管理资源生命周期——尽可能并行初始化，有序关闭，超时控制——而无需每个插件重新发明它。如果你正在构建任何插件系统，从三阶段生命周期和携带请求范围状态的上下文对象开始。

**将配置外部化到插件边界。**每个插件拥有自己的配置模式（通过JSON Schema或Zod验证）。内核合并用户配置、环境变量和默认值，然后将冻结的配置对象传递给`initialize`。这消除了“这个设置在哪里？”的蔓延，并使插件自我文档化。该模式可扩展：一个50个插件的系统仍然可导航，因为每个旋钮都有一个声明的所有者。

### 生态系统与相关项目

**LangChain**（90k+星）——最直接的比较。LangChain使用类继承和链进行组合；Harness使用插件和注册表。LangChain优化为“快速启动预构建链”；Harness优化为“独立大规模组合和替换部件”。它们解决相邻问题：LangChain用于快速原型设计，Harness用于需要在不重写生成器的情况下更换检索器的生产系统。

**AutoGen**（30k+星）——微软的多代理框架。AutoGen专注于代理到代理的对话模式（群聊、嵌套聊天）。Harness专注于单代理能力组合。它们互补：Harness可以提供AutoGen代理消费的插件化工具层，而AutoGen提供Harness不指定的多代理编排。

**Semantic Kernel**（20k+星）——微软的.NET/Python规划器+插件框架。具有“一切都是插件”的哲学，但与特定的规划器实现和内核为中心的设计相关联。Harness在精神上更具语言通用性（TypeScript核心，插件协议可以跨越语言边界），并且在规划策略上不那么有意见。值得研究Semantic Kernel的函数调用抽象以及它们如何处理原生与语义插件。

第二个关键选择是**所有文档类型共享一个公式引擎**。大多数套件将计算隔离在电子表格中；Univer的引擎在文档、幻灯片甚至画布对象中评估公式。这意味着单元格引用可以存在于幻灯片文本框中，文档段落可以计算`=SUM(A1:A10)`，代理可以在任何地方注入计算值而无需格式转换。架构通过将依赖图与网格模型解耦来实现这一点——公式引用命名范围和跨表标识符，而不是硬编码坐标。牺牲是启动延迟：即使在纯文档工作负载中，引擎也会加载。团队通过动态导入和仅当代理仅需要计算时完全树摇晃渲染器来缓解这一点。

- **项目地址**: [https://github.com/comfyanonymous/ComfyUI_examples](https://github.com/comfyanonymous/ComfyUI_examples)
- **基本数据**: `HTML` | ⭐️ 4,579 () | **来源**: `llm_giant`
- **入选理由**: *官方工作流示例集，对理解 ComfyUI 节点编排逻辑有参考价值，但本质是示例合集而非原创工具。*

### 核心痛点解决

ComfyUI 的节点-图形范式将思维模型从线性脚本转变为有向无环图组合。大多数来自 Automatic1111 或网页 UI 的用户会遇到障碍：他们理解单个节点，但无法预测潜在张量如何在分支图中流动，条件合并发生在何处，或为什么 ControlNet 注入点很重要。这个仓库通过提供可执行的参考图来解决“空白画布”问题，这些图展示了实际的组合模式——从文本到图片时的细化链式组合、从图片到图片时的去噪调度、带有加权条件的 ControlNet 堆叠——使开发人员可以克隆、执行和剖析，而不是从屏幕截图中逆向工程。

### 设计与架构权衡

工作流以 ComfyUI 的原生 JSON 格式存储，但通过静态 HTML 查看器解析和显示图形拓扑。这将可执行的实体与其文档解耦：JSON 仍然是执行的单一来源真相，而 HTML 层则添加了搜索、分类和视觉节点预览，无需运行 ComfyUI 实例。权衡在于维护摩擦——每次工作流更新都需要重新生成 HTML 视图，但它避免了为文档嵌入完整 ComfyUI 前端的更重选择。分类税则（从文本到图片、从图片到图片、ControlNet、修复、放大、视频等）反映了用户实际需要的控制流模式，而不仅仅是功能检查表。

### 工程见解与可转移的教训

基于图形的系统需要 *可执行的文档*——静态图表会立即腐烂，因为它们无法验证张量形状、数据类型兼容性或节点版本漂移。通过将工作流作为可运行的 JSON 发送，这个仓库将示例转换为回归测试：如果核心节点更改其输入签名，损坏的示例会立即暴露出回归问题。更深层次的教训是：当你的 API 是一个图形时，你的文档也必须是一个图形。这适用于任何基于节点的编排层（LangGraph、Dagster、Airflow DAG、着色器图形）。投资于一个“加载和验证”的 CI 步骤，该步骤实例化每个示例图形并验证结构完整性——它捕获了单元测试在单个节点上遗漏的静默契约违规。

### 生态系统与相关项目

**comfyanonymous/ComfyUI**（45k+ 星）——运行时引擎本身。没有它，这些示例毫无意义；工作流 JSON 引用了仅存在于 ComfyUI 生态系统中的自定义节点类型。理解核心调度器的执行顺序（拓扑排序结合批处理感知优化）解释了为什么这些示例中的某些节点排列是高效的，而其他排列会导致死锁。

**ltdrdata/ComfyUI-Manager**（10k+ 星）——自定义节点的包管理器。大多数这里的示例依赖于核心之外的节点（ControlNet、IPAdapter、AnimateDiff、UltimateSDUpscale）。ComfyUI-Manager 在安装时解析依赖图，将工作流的隐式节点需求转换为显式的、可重复的环境——“示例在我机器上工作”与“示例在 CI 中工作”之间的缺失环节。

**Fannovel16/ComfyUI-ControlNet-Aux**（3k+ 星）——ControlNet 工作流的预处理器集合。这个仓库中的 ControlNet 示例假设特定的预处理器（OpenPose、Depth、Canny、LineArt），这些预处理器存在于这个单独的仓库中。它展示了关键的架构模式：将预处理（CPU 绑定、模型无关）与 ControlNet 注入（GPU 绑定、模型特定）分离，使预处理器的缓存和替换无需重写下游图形成为可能。

### 🔹 [B] meta-llama/PurpleLlama
- **项目地址**: [https://github.com/meta-llama/PurpleLlama](https://github.com/meta-llama/PurpleLlama)
- **基本数据**: `Python` | ⭐️ 4,404 () | **来源**: `llm_giant`
- **入选理由**: *LLM 安全评估工具集，对做 Agent 系统的安全边界设计有参考意义，但使用场景相对垂直。*

### 核心痛点解决

LLM 安全与传统软件安全不同。你无法为“当模型在创造性提示下泄露 PII 时”或“如果我将其作为编程练习框架，模型是否会生成 SQL 注入负载”编写单元测试。攻击面是概率性的、上下文相关的，并随着模型获得的新能力而增长。当团队在构建代理系统时意识到他们的护栏——通常是正则表达式过滤器或提示指令——在对抗性压力下蒸发时，他们遇到了这一障碍。PurpleLlama 解决了测量缺口：你无法改进你无法量化的部分，现有的安全工具假设确定性行为。

### 设计与架构权衡

该项目分为两个独立层次：**CyberSecEval** 用于测量和 **Llama Guard** 用于执行。这种分离是故意的。CyberSecEval 将模型视为黑盒，运行标准化提示，涵盖代码解释器滥用、提示注入和不安全代码生成等类别。它生成可比的评分——这对于模型版本之间的回归跟踪至关重要。相比之下，Llama Guard 是一个白盒防御：一个针对 14 个风险类别的分类器，经过微调，位于推理路径中，对用户输入和模型输出进行分类。权衡在于延迟和部署复杂性。分类器每轮增加约 100-200 毫秒，并需要自己的服务基础设施，但它捕捉到了模式匹配遗漏的语义攻击。团队选择单独的模型而不是基于提示的护栏，因为绕过主模型的提示注入通常也绕过了基于提示的防御——相同的架构，相同的失败模式。

### 工程见解与可转移的教训

**专门的小模型作为安全门** 是一个可以超越 Llama 的模式。这一见解是：仅针对安全分类训练的 7B 模型优于被提示为“检查不良内容”的 70B 通用模型。较小的模型没有竞争目标——没有帮助性压力，没有推理干扰。它学习到一个清晰的决策边界。这适用于你需要从未结构化的 LLM 输出中获得可靠二元信号的任何地方：PII 检测、事实一致性检查、政策合规性。架构模式是：**大模型生成 → 小型专业化模型验证 → 路由或拒绝**。它保持了快速路径的快速（大多数请求通过），同时限制了失败的范围。

**紫队作为一门学科** —— 将红队攻击与蓝队防御结合在同一评估循环中——迫使诚实。如果你只进行红队测试，你会收集没有缓解路径的漏洞。如果你只进行蓝队测试，你会针对已知攻击加固，但对新型攻击视而不见。CyberSecEval 的基准套件成为 Llama Guard 的回归测试：当出现新的逃逸时，你将其添加到评估中，然后重新训练护栏。这种循环是唯一一种让安全跟上模型能力增长的方式。

### 生态系统与相关项目

**PromptFoo**（8k+ 星）在应用层补充了 PurpleLlama。PurpleLlama 评估模型级别的行为，而 PromptFoo 评估你的特定提示、RAG 管道和代理链与自定义测试用例的匹配度。它将你的 LLM 应用视为待测试单元——因为模型级别的安全性并不能保证应用级别的安全性，当你组合工具、上下文和多步推理时。

**Guardrails AI**（8k+ 星）实现了“小型模型验证器”模式作为声明性框架。你定义输出模式和验证器（PII、脏话、SQL 注入、自定义正则表达式），并用结构化重试逻辑包装任何 LLM 调用。它实现了上述架构见解：将验证与生成分离，使验证可配置，并在自动重试中关闭失败。

**OWASP LLM Top 10**（不是一个代码项目，但标准分类）提供了共享词汇。PurpleLlama 的 CyberSecEval 类别直接映射到 OWASP 类别（LLM01 提示注入、LLM02 不安全输出处理、LLM06 敏感数据暴露）。使用 OWASP 作为威胁模型检查表确保你的评估覆盖范围不会偏向容易测试的内容。
