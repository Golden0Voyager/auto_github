### 👑 [S] obra/superpowers
- **项目地址**: [https://github.com/obra/superpowers](https://github.com/obra/superpowers)
- **基本数据**: `Shell` | ⭐️ 291,265 (611 stars today) | **来源**: `trending`
- **入选理由**: *29 万星的 Agent 技能框架，不只是工具而是方法论——定义了 Agent 如何获取和组合技能，对设计 Agent 能力扩展机制有直接参考价值。*

### 核心痛点解决

构建可靠的AI代理意味着面对一个碎片化的环境：每个框架都有自己定义工具、管理上下文、处理错误和组合能力的方式。你最终在写粘合代码而不是解决实际问题。Superpowers通过将技能视为具有明确契约的一级可组合单元来重新定义这一点——输入、输出、副作用和失败模式都在一开始就声明。它解决的痛苦不是“我如何调用一个LLM”，而是“如何构建一个系统，在能力可以被发现、组合和调试而无需每次需求变化时重写编排层。”

### 设计与架构权衡

该框架选择**声明式技能清单**而非命令式注册。每个技能都位于自己的目录中，其中包含一个`manifest.yaml`文件，描述其接口、依赖项和执行模型。这种做法牺牲了启动灵活性以换取静态可分析性：在任何一次LLM调用之前，你可以验证整个技能图，捕获循环依赖关系，并自动生成文档。代价是动态加载技能在运行时需要重新加载周期——这在开发工作流中是可以接受的，但在生产中热切换时则不太合适。

执行使用**基于shell的运行时**而非嵌入特定语言的SDK。技能是可执行脚本（bash、python、node等），通过stdin/stdout JSON进行通信。这避免了供应商锁定，并允许团队为每个技能使用合适的工具——`jq`用于转换，`curl`用于HTTP，`python`用于复杂逻辑——但将复杂性推到了契约层。框架在边界处强制执行模式验证，因此Python技能的输出会在被Bash技能消费之前进行验证。你获得了多语言自由；你失去了跨语言边界的过程性能和类型安全性。

### 工程见解与可转移的教训

**明确的契约使组合成为可能。**大多数代理框架将工具视为不透明的函数。通过要求每个技能声明其输入/输出模式、先决条件和幂等性保证，Superpowers将组合问题转化为机械验证问题，而不是提示工程赌博。这一原则适用于任何将异构组件拼接在一起的地方：微服务、CI/CD步骤、数据管道。如果你不能静态验证握手，你就是在生产中调试。

**方法论胜于库。**仓库中包含一个`CLAUDE.md`文件，其中规定了如何*思考*技能设计——粒度规则、命名约定、错误处理模式、测试策略。代码薄；纪律严。这反映了成功平台团队的发现：框架不如它强制执行的约定重要。当你设计自己的内部平台时，在抽象层之前投资于“我们这里如何做事”的文档。

**shell作为集成胶水。**使用shell脚本作为编排层听起来过时，直到你意识到它迫使每个技能成为一个独立的CLI。这种约束产生了可以在隔离环境中测试、由人类脚本化并跨环境移植的技能。教训是：有时最持久的契约是“原始”接口（stdin/stdout、退出代码、环境变量），因为它对调用者的假设最少。

### 生态系统与相关项目

**langchain-ai/langchain**（90k+星）——主导的代理编排框架。Superpowers提供了一种方法论和轻量级运行时，而LangChain提供了一个厚重的SDK，带有预构建的集成、记忆模块和链/代理抽象。它们相辅相成：Superpowers定义了*如何*结构化技能；LangChain提供了*要插入的*技能（向量存储、工具包、模型封装）。一个团队可以使用Superpowers的清单规范将LangChain组件封装为可移植的技能。

**anthropics/claude-code**（最近，高可见度）——Anthropic的编码代理，直接在你的仓库中运行。它体现了Superpowers正式化的“代理作为熟练操作员”的模型：离散的能力（读取、写入、grep、bash、待办事项）和明确的契约。研究Claude Code内置的工具集揭示了最小且完整的技能基础是什么样子——在设计你自己的技能分类法时很有用的参考。

**microsoft/autogen**（25k+星）——多代理对话框架。Superpowers专注于单代理技能组合；AutoGen专注于代理间协议。如果Superpowers技能是函数，AutoGen代理是服务。这两层映射清晰：每个AutoGen代理都可以作为Superpowers技能图实现，从而在不混淆关注点的情况下提供代理内的结构（Superpowers）和代理间的协调（AutoGen）。

### 👑 [S] NousResearch/hermes-agent
- **项目地址**: [https://github.com/NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)
- **基本数据**: `Python` | ⭐️ 248,758 () | **来源**: `llm_giant`
- **入选理由**: *24 万星的 Agent 框架，强调 Agent 随使用成长的能力，在记忆管理和个性化方面提供了不同于主流框架的设计思路。*

### 核心痛点解决

大多数代理框架将内存视为一种附带考虑——一个你将其填充会话历史并寄希望于最好的向量存储。当部署用户日常互动的代理时，真正的问题就出现了：它们忘记了偏好，重复错误，并且无法在没有手动提示工程的情况下建立在过去的上下文之上。赫尔梅斯代理通过将内存视为一种一等架构原语而不是附加项来解决这一问题。核心洞察是，只有当代理的内部用户模型不断演变时，其效用才会累积，而不是从上周的聊天中检索静态嵌入。

### 设计与架构权衡

该框架使用双存储架构将*情景记忆*（发生了什么）与*语义记忆*（用户偏好、思维方式、重复模式）区分开来。情景数据存储在一个按时间分区的事件日志中，优化了大量追加写入和时间查询；语义记忆则使用知识图谱，其中实体为用户偏好、工作流和通过LLM驱动的反思循环提取的隐式规则。这种划分牺牲了查询的简单性——你不能简单地对所有内容进行`相似性搜索`——但获得了对什么持久化、什么衰减以及什么被提升到长期模式的精确控制。反思循环异步运行，由交互量阈值触发，而不是固定的时间表，这避免了代理自信地应用过时用户模型的“陈旧记忆”问题。

### 工程见解与可转移的教训

**记忆提升标准应明确，而非启发式。** 赫尔梅斯代理定义了清晰的提升规则：一个模式必须出现在N个不同的会话中，通过矛盾检查并经过一致性验证后才能进入语义记忆。这防止了一次性用户怪癖成为永久的“偏好”。可转移的教训是：将记忆写入视为模式迁移——版本化、验证和可逆的。如果代理不能解释为什么它认为用户偏好X，这种信念不应持久化。

**异步反思胜过同步上下文填充。** 与其将更多标记塞入上下文窗口，该框架运行一个后台“合并”过程，重写语义记忆。这类似于人类记忆的工作方式——我们不会在每次决策前重读整个日记；我们维护一个离线更新的压缩工作模型。对于任何长期运行的代理系统，在优化检索之前，投资于合并管道。

### 生态系统与相关项目

**LangChain**（90k+星）提供了更广泛的编排层——链、工具和集成——而赫尔梅斯代理专注于记忆/个性化问题。它们可以很好地组合：LangChain处理“如何执行”，赫尔梅斯处理“为谁执行”。

**MemGPT**（15k+星）从操作系统启发的虚拟内存角度（上下文的进进出出）解决了相同的一等公民记忆问题。赫尔梅斯代理的知识图谱方法补充了MemGPT的分页：一个管理*容量*，另一个管理*意义*。

**AutoGen**（30k+星）在多代理工作流方面表现出色，但假设静态代理配置。赫尔梅斯代理不断演变的用户模型可以为AutoGen的代理定义提供输入，让专业代理能够在不重新配置的情况下随着时间的推移适应同一个用户的行为。

### 👑 [S] deepseek-ai/deepseek-harness
- **项目地址**: [https://github.com/deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)
- **基本数据**: `TypeScript` | ⭐️ 235,275 () | **来源**: `llm_giant`
- **入选理由**: *23 万星的插件化 Agent 框架，'Everything is a Plugin' 的架构让能力扩展极其灵活，是 vibecoding 工具链中插件生态设计的标杆。*

### 核心痛点解决

构建基于LLM的代理通常从简单开始：一个提示，一个工具调用，一个循环。然后需求增长。你需要记忆，检索，代码执行，浏览器自动化，也许还有自定义API封装。每个新功能意味着修改核心循环，添加条件分支，或者更糟糕的是——因为抽象无法适应而分叉框架。痛苦不在于添加第一个工具，而在于工具需要组合、共享状态或根据任务进行交换时，核心协调器需要重新布线的组合爆炸。

### 设计与架构权衡

“一切都是插件”的信条意味着协调器几乎不知道能力的任何信息。它只知道如何通过统一接口加载、初始化和调用插件。这将复杂性推到了插件边界：每个插件必须提前声明其输入模式、输出模式和副作用配置文件。这种权衡是明确的——你获得了可热插拔的能力和清晰的分离，但你需要为琐碎的工具付出样板代码，并为只想快速添加一个功能的贡献者带来陡峭的学习曲线。框架选择了模式优先的合同，而不是鸭子类型，这在加载时而不是在生产跟踪期间捕获集成错误。

状态管理是另一个故意的约束。插件不共享全局可变上下文；它们接收一个范围内的快照并返回一个增量。这使执行具有确定性和可重放性——对于调试代理循环在偏离正轨时至关重要——但迫使开发者显式地建模状态转换。你不能简单地在一个全局中存储一个值并在三步后读取它。该架构以便利为代价换取可追踪性，当你在二分法中探究代理在凌晨3点时调用工具的原因时，这会带来回报。

### 工程见解与可转移的教训

值得借鉴的模式：**通过静态清单而非运行时反射发现能力**。每个插件都附带一个清单（JSON或TypeScript装饰器），描述它做什么，需要什么，以及它产生什么。协调器在启动时构建能力图，使在生成任何令牌之前就能自动选择工具、解决依赖关系和检测冲突。这将“这个工具存在吗？”和“这些工具能否组合？”从运行时失败转移到部署时验证。将此应用于任何动态组合行为的地方：CI管道、功能标志、微前端或任何插件系统，其中意外集成会导致生产事故。

第二个教训：**将插件边界作为序列化边界**。如果插件的输入和输出设计为可序列化，你将免费获得日志记录、重放、缓存和分布式执行。框架通过要求映射到JSON可序列化类型的模式来强制执行这一点。抵制传递类实例或闭包到边界——一旦这样做，你就失去了检查、重放或跨进程移动执行的能力。

### 生态系统与相关项目

**LangChain**（90k+星）——最成熟的代理协调框架。DeepSeek Harness 使用插件作为原子单元，而 LangChain 使用链和代理作为可组合的基本单元。它们解决类似的问题，但 Harness 的插件优先方法使能力发现和热插拔更加明确；LangChain 的生态系统深度意味着更多的预构建集成开箱即用。

**AutoGen**（30k+星）——微软的多代理对话框架。它专注于代理到代理的对话模式，而不是工具插件。Harness 可以将 AutoGen 作为“插件”用于多代理辩论或协作场景，而 AutoGen 则从 Harness 的插件生态系统中受益于工具访问。

**Semantic Kernel**（20k+星）——微软的嵌入AI到应用程序的SDK，具有强大的计划者和技能/插件模型。它的“技能”概念与 Harness 的插件非常接近，但 Semantic Kernel 首先针对 .NET 和 Python 企业集成。这两个项目都认识到**计划和执行应该是分开的问题**——Harness 通过插件清单实现这一点，Semantic Kernel 通过其计划者抽象实现这一点。

### 👑 [S] stablyai/orca
- **项目地址**: [https://github.com/stablyai/orca](https://github.com/stablyai/orca)
- **基本数据**: `TypeScript` | ⭐️ 77,614 (6,547 stars this week) | **来源**: `trending`
- **入选理由**: *并行 Agent 的 ADE（Agent Development Environment），支持桌面、移动端和远程运行时，是 vibecoding 工作流从单 Agent 走向多 Agent 编排的关键基础设施。*

### 核心痛点解决

你曾感受到单代理工作流的摩擦：一项任务接一项任务，上下文窗口溢出，无法并行化独立工作流。真正的痛点不是运行代理，而是协调一整套代理。当你启动三个代理来重构不同模块时，你需要手动拼接输出，解决冲突，并追踪哪个代理修改了什么。现有的IDE将代理视为聊天侧边栏，而不是一级并行工作者。Orca 重新定义了这一点：环境本身就是协调者，而不是代理主机。

### 设计与架构权衡

BYO（自带）订阅模型是关键的架构决策。Orca 不将你锁定在一个带有按词计费的管理推理API中，而是连接到你现有的Claude、OpenAI或本地模型凭证。这牺牲了统一计费仪表板的便利性，但获得了两个关键属性：大规模的成本可预测性和在模型选择上零供应商锁定。对于运行数十个并行代理的团队，直接API访问与加价平台的成本差异迅速累积。

跨平台运行时（桌面、移动、远程）采用客户端-服务器架构，其中繁重的协调逻辑运行在Node.js后端，而前端保持轻量。这避免了在Electron、React Native和Web客户端中重复代理协调逻辑。权衡之处在于：远程运行时设置需要基础设施意识——SSH隧道、Docker或云虚拟机，这提高了非技术人员的门槛，但为工程团队提供了真正的“随处运行”语义。

### 工程见解与可转移的教训

**代理协调是一个状态机问题，而不是聊天问题。**Orca 将每个代理视为具有显式生命周期事件的状态工作者：启动、上下文注入、工具执行、检查点、合并。这可以清晰地映射到行为模型并发——每个代理拥有其上下文切片，通过结构化消息进行通信，并将检查点保存到共享存储中。教训是：在添加功能之前，为代理生命周期投资一个正式的状态机。随意的提示链在超过三个并行工作者后变得难以维护。

### 🔥 [A] google/ax
- **项目地址**: [https://github.com/google/ax](https://github.com/google/ax)
- **基本数据**: `Go` | ⭐️ 10,569 (1,373 stars today) | **来源**: `trending`
- **入选理由**: *Google 开源的 Agent 编排运行时，用 Go 实现，关注多 Agent 调度和状态管理，适合需要生产级 Agent 编排的团队参考架构设计。*

### 核心痛点解决

构建由多个LLM代理组成的生产系统迅速暴露出一个差距：代理本身很容易原型化，但可靠地协调它们却不是那么容易。最终，你需要编写自定义的粘合代码来处理任务队列、重试逻辑、状态持久化和代理间通信——基本上是从头开始重建一个分布式系统运行时。大多数团队要么接受脆弱的编排，要么投入数月时间构建不是其核心产品的基础设施。ax通过提供一个专门构建的运行时来处理编排问题（调度、状态、可观测性），使你能够专注于代理逻辑。

### 设计与架构权衡

选择Go而非Python反映了对操作特性优先于生态系统熟悉度的刻意权衡。Go的编译二进制部署、内置并发原语和可预测的内存配置使ax在生产Kubernetes环境中作为边车或独立服务运行时，无需拖带Python运行时及其依赖链变得更容易。代价是LLM原生库的池子较小，但ax通过暴露干净的gRPC/HTTP接口来缓解这一问题——代理可以用任何语言编写，并通过明确的契约与运行时通信。

状态管理使用事件源模型而不是简单的键值存储。每个代理转换、工具调用和决策都被持久化为不可变事件。这增加了写入开销，但使时间旅行调试、精确回放用于回归测试以及受监管环境中所需的审计跟踪成为可能。牺牲是热路径上的延迟；ax通过异步持久化和内存快照来为活跃工作流补偿。

### 工程见解与可迁移的教训

**分离编排与执行。** 运行时不应知道代理是如何推理的——只需知道它需要被调度、其状态被跟踪以及其输出被路由。这种控制反转让你可以在不接触编排层的情况下，用不同的代理实现（LangChain、自定义Go，甚至是外部API）进行替换。实践中，定义一个最小的代理接口（输入 → 输出 + 元数据），并围绕该契约构建运行时。

**将代理工作流视为持久状态机。** 瞬态内存工作流在真实负载下会失败：pod重启、网络分区和人工干预延迟会打破单一请求-响应循环的幻觉。将每个状态转换持久化为事件——不仅仅是最终结果——将脆弱的链变成可恢复的过程。该模式不仅适用于代理：任何长期运行、多步骤操作（CI流水线、订单履行、数据处理）都从相同的持久性保证中受益。

### 生态系统与相关项目

**Temporal**（30k+星）——持久执行的黄金标准。虽然ax专注于特定于代理的模式（工具调用、LLM上下文管理），但Temporal提供了底层的工作流引擎，具有经过实战验证的保证。团队通常在Temporal之上运行ax，或者采用Temporal的模式（活动、信号、查询）来构建自己的编排层。

**LangGraph**（8k+星）——LangChain的基于图的编排库。它解决了类似协调问题，但保持在Python/LangChain生态系统内。将ax的Go运行时方法与LangGraph的Python库进行比较，揭示了语言无关的运行时与框架集成库之间的光谱。两者都是有效的；选择取决于你是将编排作为基础设施还是作为代码。

**Dapr**（23k+星）——提供ax可以消费的构建块（状态管理、发布/订阅、工作流），而不是重新实现。如果你已经使用Dapr，ax的特定于代理的逻辑将成为在经过验证的分布式系统原语之上的一层薄薄的逻辑。

- **项目地址**: [https://github.com/meta-llama/PurpleLlama](https://github.com/meta-llama/PurpleLlama)
- **基本数据**: `Python` | ⭐️ 4,404 () | **来源**: `llm_giant`
- **入选理由**: *LLM 安全评估工具集，覆盖越狱检测、红队测试等场景，做 Agent 系统时安全层不能省，这个库提供了现成的评估管线。*

### 核心痛点解决

你构建了一个基于LLM的功能。在测试中表现优异。然后有人要求它忽略之前的指令，输出系统提示，或者生成SQL注入负载，甚至编写钓鱼邮件。模型欣然照办。你需要一个安全层，位于用户输入和模型输出之间，但从头构建一个意味着需要收集攻击数据，训练分类器，定义分类体系，并维护评估管道——而威胁环境每周都在变化。紫罗兰 llama 存在的原因是，每个基于LLM的团队都面临着同样的基础设施负担，而重复构建这些基础设施在公司之间毫无意义。

### 设计与架构权衡

核心架构决策是使用微调后的Llama模型作为安全分类器，而不是单独的BERT风格编码器或基于规则的系统。作为分类器的生成模型意味着同一个推理栈同时服务于生成和护栏——不需要单独的模型服务基础设施，也不需要维护嵌入服务。权衡在于延迟：Llama Guard 每次请求增加一次完整的前向传递。对于高吞吐量的应用程序，这迫使你在这两种选择之间做出选择：异步护栏评估（冒着竞争条件的风险）或接受每次轮次100-300毫秒的额外开销。分类体系设计也反映了实际的妥协：14个安全类别涵盖了暴力、色情内容、个人身份信息（PII）和代码漏洞，但故意排除了“虚假信息”这类存在争议的类别，因为错误的正例会摧毁用户信任。

### 工程见解与可转移的教训

最可转移的模式是将安全性视为评估问题，建模问题其次。紫罗兰 llama 在提供Llama Guard权重之前，就提供了CyberSecEval——标准化的代码解释器滥用、提示注入和不安全代码生成基准。这强制了一种纪律：定义“安全”的含义是可量化的，然后构建检测器来推动这些指标。当你在自己的系统中采用这种方法时，从编写针对特定失败模式的评估开始（例如，“当要求调试时，代理是否会泄露API密钥？”），而不是直接使用通用的安全模型。第二个教训是：安全分类器需要在训练数据中包含版本化的分类标签。Llama Guard的训练数据包括精确的类别标签作为标记，使模型的推理可检验，并且可以在不重新训练的情况下扩展分类体系，只需添加新的标记示例并微调。
